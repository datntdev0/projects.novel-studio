1. PrinciplesNguyên tắc

  • Local-first, no server of ours. Everything the user owns (novels, story world, translations, media, settings, job history) lives in one library folder on their disk; the only network traffic is made by the AI CLIs with the user's own login (constraints, NG1, NG4, A10). The Python backend is a local process on 127.0.0.1, not a server anyone else can reach.
  • Local-first, không có máy chủ của chúng ta. Mọi thứ thuộc về người dùng (tiểu thuyết, thế giới truyện, bản dịch, media, cài đặt, lịch sử tác vụ) nằm trong một thư mục thư viện trên đĩa của họ; lưu lượng mạng duy nhất là do các CLI AI tạo ra bằng tài khoản của chính người dùng (ràng buộc, NG1, NG4, A10). Backend Python là tiến trình cục bộ trên 127.0.0.1, không phải máy chủ mà ai khác có thể truy cập.
  • Familiar technology, few dependencies. TypeScript for the app, Python only where local models and media tools live; built-in Node modules over native add-ons; self-written small pieces (i18n, data access) over frameworks when the piece is small.
  • Công nghệ quen thuộc, ít phụ thuộc. TypeScript cho ứng dụng, Python chỉ ở nơi có mô hình cục bộ và công cụ media; ưu tiên module có sẵn của Node hơn add-on native; tự viết các phần nhỏ (i18n, truy cập dữ liệu) thay vì dùng framework khi phần đó nhỏ.
  • One deployable. A single portable zip containing the app, the Python backend and ffmpeg; nothing to install, no update server (constraints, NG4, A6).
  • Một gói triển khai duy nhất. Một tệp zip portable chứa ứng dụng, backend Python và ffmpeg; không phải cài gì, không máy chủ cập nhật (ràng buộc, NG4, A6).
  • The UI never waits for work. Every external capability runs behind a service in the Electron main process (CLI child process or Python HTTP job); the renderer only receives progress events, so a 100-chapter run (A2, A11) can never freeze the studio.
  • Giao diện không bao giờ chờ công việc. Mọi năng lực bên ngoài chạy sau một service trong tiến trình chính của Electron (tiến trình con CLI hoặc tác vụ HTTP của Python); renderer chỉ nhận sự kiện tiến độ, nên một lần chạy 100 chương (A2, A11) không bao giờ làm treo studio.
  • Plain files, one index. Chapters, covers, images, audio, video and exports stay as ordinary files in the per-novel folder; metadata, story world, relations and job state live in one embedded SQLite file sized for ~3,000 chapters per novel and tens of novels (A2).
  • Tệp thuần, một chỉ mục. Chương, bìa, hình ảnh, âm thanh, video và tệp xuất là tệp bình thường trong thư mục của từng truyện; siêu dữ liệu, thế giới truyện, quan hệ và trạng thái tác vụ nằm trong một tệp SQLite nhúng tính cho ~3.000 chương mỗi truyện và hàng chục truyện (A2).
  • Everything testable with playwright-cli. The renderer runs in a plain browser against an in-memory bridge, and every capability gets a fake implementation from the module that first needs it, so each acceptance criterion can be driven end to end without AI quota, Python or ffmpeg.
  • Mọi thứ kiểm thử được bằng playwright-cli. Renderer chạy trong trình duyệt thường với một bridge trong bộ nhớ, và mỗi năng lực có bản giả lập do module đầu tiên cần nó xây, nên mọi tiêu chí chấp nhận đều chạy được từ đầu đến cuối mà không cần hạn mức AI, Python hay ffmpeg.
  • Code that follows CLAUDE.md by default. Formatter and linter settings make the guidelines (no comments on members, single-line imports, no Omit, data-testid everywhere) the path of least resistance.
  • Mã nguồn mặc định tuân theo CLAUDE.md. Cấu hình formatter và linter biến các hướng dẫn (không chú thích thành viên, import một dòng, không dùng Omit, data-testid ở mọi nơi) thành con đường dễ đi nhất.

3. System contextBối cảnh hệ thống

One user, one desktop app, one library folder. The app spawns three kinds of local processes: the two AI CLIs (per job item) and the Python backend (for the whole session). Only the CLIs reach the network, with the login the user created outside the app (A3, A8). There is no Novel Studio server anywhere.

Một người dùng, một ứng dụng desktop, một thư mục thư viện. Ứng dụng tạo ba loại tiến trình cục bộ: hai CLI AI (theo từng mục tác vụ) và backend Python (cho cả phiên làm việc). Chỉ các CLI kết nối mạng, bằng tài khoản người dùng đã đăng nhập bên ngoài ứng dụng (A3, A8). Không có máy chủ Novel Studio ở bất cứ đâu.

In release 1 only the CLIs reach the network. From Release 9 (TH-11, TH-12) two more paths open: the Python backend reaches the media platforms the user designates (M19), and main reaches publishing platforms (M20) with credentials kept encrypted through Electron safeStorage (Windows DPAPI) [unverified]; the renderer still never opens a socket. Figure 1 shows the release-1 shape.

Trong bản 1 chỉ các CLI kết nối mạng. Từ Release 9 (TH-11, TH-12) mở thêm hai đường: backend Python kết nối tới các nền tảng media do người dùng chỉ định (M19), và main kết nối tới các nền tảng xuất bản (M20) với thông tin đăng nhập được mã hóa qua Electron safeStorage (Windows DPAPI) [unverified]; renderer vẫn không bao giờ mở socket. Angular renderer · angular/

Responsibility: the studio UI. Owns: the shell (panels, command palette, shortcuts, theme, language, status bar with the job item), one feature folder per module (M01–M22), signal stores, Bootstrap SCSS build, the Angular I18nService and t pipe (src/app/core/i18n), data-testids. Talks to: the Bridge interface from @shared/core only; in Electron it is the preload bridge, in a browser it is BrowserBridge (in-memory fake used by playwright-cli).

Trách nhiệm: giao diện studio. Sở hữu: phần vỏ (bảng điều khiển, bảng lệnh, phím tắt, giao diện sáng tối, ngôn ngữ, thanh trạng thái với mục job), mỗi module (M01–M22) một thư mục tính năng, store bằng signal, build Bootstrap SCSS, I18nService và pipe t của Angular (src/app/core/i18n), các data-testid. Giao tiếp với: chỉ giao diện Bridge từ @shared/core; trong Electron là cầu nối preload, trong trình duyệt là BrowserBridge (giả lập trong bộ nhớ dùng cho playwright-cli).

Preload bridge · electron/src/preload.ts

Responsibility: the only door between renderer and main. General long-running process flow (TH-01 framework built by M03, used by every job)Luồng tiến trình chạy dài tổng quát (khung TH-01 do M03 xây, dùng cho mọi tác vụ)

  1. UI action. The user starts a run from a feature screen; the renderer sends job:start with the capability, the service chosen in Settings (TH-03), and the item range.
  2. Thao tác giao diện. Người dùng bắt đầu một lượt chạy từ màn hình tính năng; renderer gửi job:start với năng lực, service đã chọn trong Cài đặt (TH-03) và khoảng mục.
  3. IPC. The preload forwards the typed request to ipcMain.handle; the handler validates it and hands it to the job runner.
  4. IPC. Preload chuyển yêu cầu có kiểu tới ipcMain.handle; handler kiểm tra và giao cho bộ chạy tác vụ.
  5. Queued in main. One jobs row and one job_items row per item are written before the call returns, so the work exists on disk before anything runs.
  6. Xếp hàng ở main. Một dòng jobs và mỗi mục một dòng job_items được ghi trước khi lời gọi trả về, nên công việc đã tồn tại trên đĩa trước khi bất cứ thứ gì chạy.
  7. Executed by a service. The worker pool takes the next queued item and calls the service: an LLM item spawns one CLI child process and reads its stdout; a media item posts a job to the Python backend and subscribes to its SSE events. Item granularity for LLM work may be revisited in the TH-04 flow.
  8. Service thực thi. Nhóm worker lấy mục đang chờ kế tiếp và gọi service: mục LLM tạo một tiến trình con CLI và đọc stdout; mục media gửi tác vụ tới backend Python và đăng ký sự kiện SSE của nó. Độ mịn của mục cho công việc LLM có thể xem lại trong flow TH-04.
  9. Streamed progress. Main emits job:progress (job id, done / failed / total, current item, short message) after every item or backend event, throttled to ≤ 10 per second; the status-bar job item, the Task Center screen and the feature screen subscribe through the bridge.
  10. Tiến độ theo luồng. Main phát job:progress (id tác vụ, xong / lỗi / tổng, mục hiện tại, thông điệp ngắn) sau mỗi mục hoặc sự kiện backend, giới hạn ≤ 10 lần mỗi giây; mục job trên thanh trạng thái, màn hình Task Center và màn hình tính năng đăng ký qua bridge.
  11. Persisted results. The result file is written to *.tmp and renamed first; then rows and the item state change in one SQLite transaction. A crash between the two leaves an orphan file that the next run overwrites.
  12. Kết quả được lưu. Tệp kết quả được ghi ra *.tmp và đổi tên trước; sau đó các dòng và trạng thái mục đổi trong một giao dịch SQLite. Sự cố giữa hai bước chỉ để lại một tệp mồ côi mà lượt chạy sau sẽ ghi đè.
  13. Resumable. Because state is per item, cancel, crash, quota error or closing the app loses at most the item in flight; on open, running items return to queued, and resuming continues the same job id (A11).
  14. Tiếp tục được. Vì trạng thái tính theo từng mục, việc hủy, sự cố, lỗi hạn mức hay đóng ứng dụng chỉ mất nhiều nhất mục đang chạy; khi mở lại, các mục running trở về queued, và tiếp tục sẽ chạy với cùng id tác vụ (A11).
